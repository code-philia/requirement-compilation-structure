模型调用实践

两个任务，
比较模型效果与开销

任务一：整理订单 CSV
任务二：生成建筑日照分析应用

同一份提示词，尝试不同模型和思考设置，
同时观察结果质量、Token、金额与等待时间。

实验模型：DeepSeek Flash / DeepSeek V4 Pro / Qwen3.7 Flash

任务一 · 数据整理

把一张有异常的订单表，整理成统计报告

输入：16 条虚构订单，CSV 原文已包含在任务提示词中。

  • 清洗格式：空白、状态大小写、日期格式、价格千位逗号。
  • 校验数据：重复订单、空城市、异常数量、负价格、错误日期和邮箱。
  • 输出结果：有效订单统计、城市销售额，以及逐行错误明细。

重点：先判断哪些数据有效，再统计；无法确认的错误不猜测修复。

任务一 · 操作

相同数据，依次交给三个模型

  1. 进入「任务」页，展开「订单数据整理」，点击填入工作台。
  2. 选择模型，先关闭思考，点击「发送」。
  3. 核对统计与错误报告，查看右侧的耗时、Token 和金额。
  4. 保持提示词不变，更换模型；再开启思考，观察结果是否改变。

标准答案在任务页直接展示。每次发送是独立请求，不携带之前的对话。

任务一 · 结果观察

先核对答案，再比较开销

标准结果

16 条原始订单
= 7 条有效 + 1 条重复 + 8 条错误

有效已支付：5 单、9 件
销售额：¥2660.80

错误行共 8 条，错误项共 9 项。

可能观察到

  • 不同模型都能答对，但时间和金额不同。
  • 漏报一行中的多个错误，或把重复订单算进销售额。
  • 开启思考增加用量，却未改善正确率。

注意：0 元赠品合法；待支付与已取消订单不计销售额。右侧“已完成”仅表示调用结束。

任务二 · 3D 应用生成

从提示词生成一个可交互的三维应用

  • 三维场景：明亮白色背景，建筑群、太阳、实时阴影。
  • 基础分析：调节时间、季节与建筑高度，查看阴影和地面日照率。
  • 场景编辑：新增、选择、移动建筑，观察遮挡与统计联动。
  • 自主发挥：建筑细节、材质光影、场地景观与编辑辅助。

交付一份完整 HTML，在工作台的「应用预览」中直接操作。Three.js 由平台本地提供。

任务二 · 操作

生成之后，亲自操作应用

  1. 在「任务」页将建筑日照任务填入工作台，选模型并发送。
  2. 等待回复完成，打开应用预览，拖动与缩放观察场景。
  3. 把 A 楼从 24 米改为 48 米，再切换时间和季节，检查阴影与指标。
  4. 新增并移动建筑，操作暂停、继续和重置，检查功能是否真实联动。
  5. 更换模型或思考设置，重复同样操作，比较完成度与开销。

基础核对：春秋正午太阳高度 55°；A 楼理论影长应由约 16.8 米变为约 33.6 米。

第二节 · 结果讨论

哪个阶段更贵？为什么？

  • 可能一：单价更低，但多次修复使总金额或耗时增加。
  • 可能二：单价更高，但调用更少，结果更完整。
  • 可能三：前面的设计不同，影响后面实现与验收的难度。
  • 可能四：某轮费用更低，是因为失败后没有完成相同工作。

结合产物、验收、调用记录与账单，
解释一次真实的模型差异。

以上均为可能结果。一次实验不代表稳定表现；后续重复实验时，继续保持输入与比较条件一致。

失败原因不同，下一步也不同

看到的反馈先检查下一步

第三节 · 修复应用

用具体反馈提出修复要求

  1. 在失败的测试结果下，点击填入修复反馈。
  2. 在右上方「修复反馈」中，核对失败步骤、预期值与实际值。
  3. 保留原测试，点击启动应用修复。
  4. 等待主对话显示修改说明与局部代码修改建议。

也可以手动粘贴反馈，并补充：
“修复全部费用合计，保留筛选、编辑、删除与提交功能，不修改测试。”

反馈应描述发生了什么，而不是只说“测试失败了”。模型返回修改建议后，还需要人工应用。

第三节 · 应用修改

模型提出建议，人决定是否应用

  1. 阅读修改说明，展开替换前 / 替换后。
  2. 确认修改针对合计计算，未删掉原有功能，也未修改测试。
  3. 点击Apply · 应用修改，确认出现“已应用”与新的修订号。
修改前：只取最后一笔费用金额。
修改后：把所有费用金额累加，再按两位小数展示。

预期：应用源码发生局部变化，测试脚本保持不变。

只收到回复而未点击 Apply，应用不会改变。若提示代码不匹配，应让模型基于当前源码重新提出修改。

第三节 · 再次执行

从失败到通过，要有验证证据

  1. 回到右上方「Playwright 测试」，确认仍为原来的三个用例。
  2. 再次点击执行测试，观察自动化过程。
  3. 核对本轮结果：合计、删除、空名称校验三个基础用例均应通过。
  4. 切换「手动操作」，亲自添加两笔费用，再核对合计。

预期：两笔合计 ¥20.00；删除交通费后为 ¥7.50；
空名称提交被阻止，原有功能仍可使用。

若仍失败，继续反馈、审阅、Apply、复测。刷新后清单为空是当前应用的设计；“模型说修好了”不能替代测试结果。

第三节 · 增加覆盖范围

一个合计用例，无法覆盖全部业务

增加的测试操作要点正确结果
分类筛选交通费 12.50 元、餐饮费 7.50 元；只筛选交通显示一笔；全部合计 ¥20.00，筛选合计 ¥12.50
缺发票批量提交两笔费用中一笔无发票，选中两笔提交整批被阻止，不应只提交有发票的一笔
提交后状态补全发票后提交，再撤回提交后不可编辑、删除；撤回后恢复可操作

让模型保留原有用例，增加上述测试，再执行全部用例。

这些功能在初始应用中已有实现，新增测试可能直接通过。不要预设每条测试一定失败；以实际行为为准。

第三节 · 测试驱动开发

新增一个规则：单笔费用最多 1000 元

新增验收规则：单笔费用金额不得超过 1000 元。
请保留原有测试，新增两个独立用例：
1. 金额 1000.00 元可以添加成功。
2. 金额 1000.01 元不能添加，提示“单笔金额不能超过1000元”，费用列表仍为空。

前半节修复已有缺陷；这里先为新规则写测试，再补实现，完整经历“失败 → 通过 → 回归检查”的测试驱动流程。

第三节 · 课堂核对

用结果说明应用为什么可以交付

  • 测试依据：操作、输入和预期结果，是否来自明确的业务要求？
  • 失败证据：能否指出具体失败步骤，以及预期值与实际值？
  • 修改证据：是否查看并 Apply 了应用修改，保持正确测试不变？
  • 验证结果：新规则通过后，原有用例是否也全部通过？

发送 → 填入测试区 → 执行测试 → 填入修复反馈
→ 启动应用修复 → 审阅并 Apply → 再次执行

测试通过只说明已检查的场景符合预期。未覆盖的业务、视觉效果和其他环境，仍需相应检查。

第四节 · 什么是好的需求

把“想要什么”说到可以核对

含糊的描述可以继续完善的描述
做一个好用的费用管理系统单人登记费用，按日期和分类查询，并查看金额合计
金额要合理金额大于零，最多两位小数；超过 1000 元时拒绝保存并提示原因
筛选之后显示统计筛选合计只统计可见记录；全部费用合计保持不变
删除后处理好数据删除该记录并更新合计；刷新后该记录不再出现

好需求应当清楚、一致、有边界、可以验收。数字和规则由业务确认；模型建议不等于已经确认。

第四节 · 如何描述

先回答六个问题，再让模型写文档

  • 谁使用：什么角色，在什么场景下使用？
  • 做什么：从哪里进入，输入什么，执行什么操作？
  • 按什么规则：金额、日期、权限、重复与状态如何判断？
  • 得到什么：页面显示什么，数据怎样变化，刷新后怎样？
  • 失败怎么办：输入错误、条件不满足时，提示什么，保留什么？
  • 这次不做什么：明确排除的功能，以及仍需确认的问题。

不清楚的地方可以先标记“待确认”，继续追问。不要用没有依据的默认规则填满文档。

第四节 · 如何拆解

按业务拆解，直到可以独立验收

个人费用登记

费用记录
　新增费用
　编辑费用
　删除费用

查询统计
　按条件筛选
　查看金额汇总

拆解时检查

  • 父节点组织范围，叶子描述具体行为。
  • 同一规则归属明确，避免多个节点各写一套。
  • 一个叶子尽量能单独说明、实现和验收。
  • 共享规则应说明关联和适用范围。

当前编译器按叶子分析业务，具体场景放在对应叶子。数据库、接口与页面结构会在后续阶段设计。

第四节 · 场景描述

用 Given / When / Then 写清验收

场景前置条件 Given用户操作 When预期结果 Then
正常清单为空，名称、分类、日期均有效新增交通费 12.50 元保存一条记录，合计 ¥12.50，刷新后仍存在
异常名称未填写，其余输入有效点击保存提示名称必填；不新增记录，合计不变
边界约定单笔上限为 1000 元分别保存 1000 和 1000.01 元前者允许，后者拒绝；两个用例独立执行

场景覆盖正常、异常和适用的边界或权限。Then 应能从界面、记录或状态核对，而不只是“处理成功”。

第四节 · 编译输入

业务文字与固定格式，各有作用

id: REQ-1
name: 录入费用
description:
  text: 名称必填，金额大于零，保存后刷新仍可查看。
scenarios:
  - id: SCN-REQ-1-01
    name: 保存有效费用
    steps:
      - id: STEP-REQ-1-01-01
        Given: 清单为空，其余必填项有效。
        When: 保存交通费，金额 12.50 元。
        Then: 新增一条记录，合计为 ¥12.50，刷新后仍存在。
        references: []
children: []

这是一个叶子节点的示例。整份文档还包含项目根节点；平台负责格式校验与导出，你负责业务规则是否准确。

第四节 · 持续维护

重要规则写进文档，讨论过程留在会话

  • 原始对话：保存在项目中，可刷新后继续查看。
  • 自动压缩：旧上下文约超过 48,000 字符时，下次发送前生成摘要。
  • 摘要内容：已确认规则、排除范围、关键术语、未决问题和当前任务。
  • 需求树：独立保存，压缩不会替换或删减节点。

展开会话上下文查看摘要，也可点击现在压缩历史。

字符数是上下文规模的近似指标，并非精确 Token 数。摘要仍需核对；关键规则确认后应落实到对应节点。

第四节 · 形成交付物

从可讨论的树，到可使用的输入文档

  2. 打开文档预览，核对业务规则和验收场景。
  3. 打开YAML，复制或下载 requirements.yaml。
  4. 工具栏可导出编译输入包；Markdown 可用于交流与评审。

预期：树、预览和导出内容一致，且能够追踪到稳定节点 ID。

参考图使用相对路径。当前 input 示例会带入对应图片；自行导入的文档如缺少资源，应在编译前补齐图片文件。

第四节 · 实现自己的需求

使用独立输入目录，运行自己的项目

  3. 设置新的输出目录，例如 outputs/my-expenses-g01。
