模型调用实践

两个任务，
比较模型效果与开销

任务一：整理订单 CSV
任务二：生成建筑日照分析应用

同一份提示词，尝试不同模型和思考设置，
同时观察结果质量、Token、金额与等待时间。

实验模型：DeepSeek Flash / DeepSeek V4 Pro / Qwen3.7 Flash

任务一 · 数据整理

把一张有异常的订单表，整理成统计报告

输入：16 条虚构订单，CSV 原文已包含在任务提示词中。

  • 清洗格式：空白、状态大小写、日期格式、价格千位逗号。
  • 校验数据：重复订单、空城市、异常数量、负价格、错误日期和邮箱。
  • 输出结果：有效订单统计、城市销售额，以及逐行错误明细。

重点：先判断哪些数据有效，再统计；无法确认的错误不猜测修复。

任务一 · 操作

相同数据，依次交给三个模型

  1. 进入「任务」页，展开「订单数据整理」，点击填入工作台。
  2. 选择模型，先关闭思考，点击「发送」。
  3. 核对统计与错误报告，查看右侧的耗时、Token 和金额。
  4. 保持提示词不变，更换模型；再开启思考，观察结果是否改变。

标准答案在任务页直接展示。每次发送是独立请求，不携带之前的对话。

任务一 · 结果观察

先核对答案，再比较开销

标准结果

16 条原始订单
= 7 条有效 + 1 条重复 + 8 条错误

有效已支付：5 单、9 件
销售额：¥2660.80

错误行共 8 条，错误项共 9 项。

可能观察到

  • 不同模型都能答对，但时间和金额不同。
  • 漏报一行中的多个错误，或把重复订单算进销售额。
  • 开启思考增加用量，却未改善正确率。

注意：0 元赠品合法；待支付与已取消订单不计销售额。右侧“已完成”仅表示调用结束。

任务二 · 3D 应用生成

从提示词生成一个可交互的三维应用

  • 三维场景：明亮白色背景，建筑群、太阳、实时阴影。
  • 基础分析：调节时间、季节与建筑高度，查看阴影和地面日照率。
  • 场景编辑：新增、选择、移动建筑，观察遮挡与统计联动。
  • 自主发挥：建筑细节、材质光影、场地景观与编辑辅助。

交付一份完整 HTML，在工作台的「应用预览」中直接操作。Three.js 由平台本地提供。

任务二 · 操作

生成之后，亲自操作应用

  1. 在「任务」页将建筑日照任务填入工作台，选模型并发送。
  2. 等待回复完成，打开应用预览，拖动与缩放观察场景。
  3. 把 A 楼从 24 米改为 48 米，再切换时间和季节，检查阴影与指标。
  4. 新增并移动建筑，操作暂停、继续和重置，检查功能是否真实联动。
  5. 更换模型或思考设置，重复同样操作，比较完成度与开销。

基础核对：春秋正午太阳高度 55°；A 楼理论影长应由约 16.8 米变为约 33.6 米。

任务二 · 结果观察

画面相似，实际完成度可能不同

观察维度完成度较高的表现可能出现的问题
渲染效果白色场景有层次，建筑细节和阴影清楚只有简单盒子，过曝或阴影难辨
基础正确性太阳、阴影、理论影长与日照率一致画面变化，数字却没有正确更新
新增与移动建筑可独立编辑，遮挡与采样随之更新只移动外观，仍用旧位置计算
连续操作暂停、继续、选择和重置相互配合选错对象、重复动画、重置有残留

以上是观察方向，不是预设胜负。以实际操作为准，源码更长或思考更多不代表结果更好。

第二节 · Flash · 观察节点一

数据库：把需求变成可保存的数据

  1. 选择 Flash、输入 input，填写第一轮输出目录。
  2. 在「执行范围」中依次选择 00、01、02、03、04，逐个运行。
  3. 浏览需求树；点击数据库实体，查看字段与关系。
  4. 打开 04 的记录，查看实现产物、验收结果和阶段开销。

观察问题：账号资料和登录会话分别保存在哪里？
密码如何保存？退出登录会改变哪些数据？

实体名称以实际产物为准。将数据设计与原始需求对应起来；数据库成功生成，还不等于整个应用已经完成。

第二节 · Flash · 观察节点二

后端：把用户操作变成接口行为

  1. 保持模型、输入和输出目录不变，依次运行 05、06。
  2. 在 API 工坊查看注册、登录、退出和查询当前用户的接口。
  3. 点击接口，追踪关联需求与数据库实体。
  4. 打开 06 的记录，查看各需求点的模型调用与验收结果。

观察问题：重复用户名、错误密码、退出后查询，
分别应该返回什么？哪些需求点发生了多次模型调用？

记录实现、验收及修复过程产生的用量。调用结束不代表验收通过；有失败时先查看具体需求点与错误。

第二节 · Flash · 观察节点三

前端：让页面与接口真正联动

  1. 沿用第一轮目录，依次运行 07、08、09、10。
  2. 查看 UI 树、页面组件与 trigger，追踪按钮关联的接口。
  3. 打开 10 的记录，检查逐需求实现与验收结果。
  4. 打开生成的应用，尝试注册、退出、错误密码登录和正确登录。

观察问题：注册完成后，首页是否显示用户名？
退出后刷新，是否仍然显示为未登录？

对照参考图观察页面，同时检查操作结果。若应用未成功生成或启动，保留失败记录并定位原因。

第二节 · Pro

换成 Pro，从初始化重新开始

  1. 选择 deepseek-v4-pro，输入仍为 input。
  2. 改用第二轮独立输出目录和端口，其余实验设置保持一致。
  3. 按相同顺序运行 00 → 10，在 04、06、10 后观察。
  4. 核对相同需求的实现结果，记录失败、修复与额外尝试。

两轮都从原始输入生成产物，不复用另一模型生成的输出。

每轮包含多次阶段运行。执行过程中不要混用输出目录，也不要在同一轮中途切换模型。

第二节 · 运行观察

从阶段账单，找到具体的模型调用

指标查看什么解释什么
阶段耗时该阶段从开始到结束的时间还包含工具执行、验收等等待
Token输入、输出，以及服务返回的缓存用量模型读了多少、生成了多少
金额平台按用量与配置单价计算的金额单价、缓存与调用量共同影响开销
调用次数阶段及需求点的模型调用数量是否存在拆解、多次实现或修复

阶段卡片直接看统计；展开调用，查看输入、回复与错误。

缺失数据不等于零开销；平台金额是按配置计价的统计值。服务账单的最终扣费以服务商为准。

第二节 · 结果讨论

哪个阶段更贵？为什么？

  • 可能一：单价更低，但多次修复使总金额或耗时增加。
  • 可能二：单价更高，但调用更少，结果更完整。
  • 可能三：前面的设计不同，影响后面实现与验收的难度。
  • 可能四：某轮费用更低，是因为失败后没有完成相同工作。

结合产物、验收、调用记录与账单，
解释一次真实的模型差异。

以上均为可能结果。一次实验不代表稳定表现；后续重复实验时，继续保持输入与比较条件一致。
