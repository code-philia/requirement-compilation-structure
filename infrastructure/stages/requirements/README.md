# 需求证据的统一消费

`images.py` 继续负责原图及发布索引/哈希；新增数据和 UI 证据层供设计、实现与验收共同使用。
正文和源文件保持原样，不能用截图或已有实现代替业务规则。

## 数据

`data.py` 将 root.data 和 data.requires 转为 `.arc/data_bindings.json`，绑定已有实体/字段，
保存生命周期、符号 ID、自然唯一键定位器、数据引用和未解决项。输入/实体设计哈希变化时
重新计算绑定。不会凭近似名称猜测非规范实体或字段。

- `SEED`：建表 SQL 完成后，智能体结合原始 data、ER 和正文实现每表 INSERT SQL。允许解释非规范实体/列名及补齐必要技术字段，保留业务原值；映射依据和假设写入 `backend/src/db/seed-evidence.json`。覆盖全部业务 SEED，并在实际初始化/重复启动时核对每个声明行。
- `CREATED`：由场景 When 操作产生，通过响应或作用域内唯一键获取实际 ID，不能全局预载。
- `DERIVED`：由真实业务处理产生；字段值在相应动作完成后验证。
- test account SEED 沿用既有身份初始化，不重复写入凭据。

平台启用时，身份/会话/审计种子文件不向业务数据智能体开放写入。数据库初始化检查会
核对每个源账号的完整角色与组织绑定，拒绝额外团队授权，不能把测试夹具写进共享身份。

显式 FK 符号引用可写为 `properties: {product_id: {$ref: DATA-PRODUCT}}`，字段须为 schema
中的 FK，目标记录实体须匹配；SEED 只能引用其他 SEED。UUID 技术主键可由符号 ID 稳定生成。
缺失技术主键由智能体确定性补齐并记录。所有 schema 属性名、必填值和实体映射都必须可核对；
仅补齐显式 SEED 所必需的父记录和技术字段，不推测业务历史。普通作用域/归属仍由平台管理，不能从业务记录名推断团队。

数据库启动检查核对规范 SEED 的已绑定字段，并检查可唯一定位的 CREATED/DERIVED 记录
没有被提前加载。没有唯一定位条件的派生结果交由真实行为验收验证，不以“碰巧相同的数量”
识别记录。后续需求的 Given 可用不同身份的局部夹具，不得占用 CREATED 的源唯一键。

WMS 的八条“入库 record”等记录由 seed 智能体解析；一个源记录可以映射到单据、明细及父表多行。页面序号和操作按钮可附理由标记为展示信息，不能将整条业务记录丢弃。只有真正矛盾或无法解释的证据才阻塞并报告。

## 页面、状态和 recipe

`ui_evidence.py` 读取 pages/index、状态、recipe 和旧设计系统观测，生成
`.arc/ui_evidence.json`，保存页面路由、菜单、状态父关系、控件契约、capture 关联、来源哈希
及缺失覆盖。原始 recipe 的表格值与行 ID 只是观察，不执行、不预加载。

每个有源图的设计页面增加 `source_page`，并通过 `source_states` 将当前需求直接引用的
状态映射到该页面真实 UI 元素；检查元素属于正确页面。多个截图状态共用页面，不膨胀成
多个路由。偏离源路由需要 `route_decision` 记录需求依据和原因。原图未采集的状态仍是
覆盖缺口，不能删除正文要求的功能。

状态显示由既有 element.data / prop.visible 和真实 React/Arco 状态实现。该 IR 不是一个
强制执行的 UI/事件 DSL。Trigger 与 E2E 同样收到页面/状态/recipe 上下文，最终仍须验证
实际表单、弹窗、行身份、导航、加载和取消行为。

Table 子树中的控件按行重复。存在性检查尊重空数组：空表没有行操作，不能靠在表外
增加重复按钮满足检查。表级工具栏放在 Table 外；真实行保留稳定元素 selector 和
独立记录身份。局部显示夹具/真实 E2E 负责正向行操作，空状态通过不等于它已经通过。

## 独立验收依据

`acceptance.py` 直接从原始需求与外部数据建立 source_expectations，E2E 保存
`.arc/acceptance_evidence.json`。它不从生成 API/页面或已有实现反推出正确业务行为。
测试生成单独获得明确的测试账号，不把测试密码放入生产 UI。

执行的测试完整标题须覆盖原始 SCN ID，且仍须断言各 Then、拒绝无写入、隔离与生命周期
结果。场景 ID 覆盖只证明没有遗漏声明，不能代替业务断言；测试审阅和真实服务验收保留。

## 上游修订

文件智能体可单独调用 `request_design_revision`，包含目标、已存在的需求 ID、来源引用、
原因和最小改动建议。记录写入 `.arc/revision_requests/`，带受影响阶段，当前任务停止。
它不赋予直接编辑 schema/API/UI/原需求或降低验收的权限。协调者按来源审阅、修订并重跑
受影响阶段；当前没有无审核的自动修改 ER 或自动批准修订功能。

smoke 恢复器只对标记 `missing_scoped_read` 的 API 修订提供窄范围自动修正：证明所有
原有操作角色都在源权限中拥有支持资源的读取能力后，补充 API 的读取能力声明，重新
验证契约并归档证据。它不改角色授权、业务效果或 ER；其他修订保持待审阅状态。

普通代码错误继续在原范围修复。编译器基础设施错误交给编译器维护，不能靠 `noCheck`
或更换 build 脚本消除失败。验收直接调用固定 TypeScript 命令并显式开启严格检查。

独立验收可发布 `.arc/acceptance_findings.json`，含与 data_bindings 一致的 `source_sha256`
以及 `items`；每项带 `requirements`、`source_refs`、`observed`、`expected`、`status`。
后端上下文只传递本需求的 OPEN 反例，源哈希不一致或引用未知需求会失败。它提供需要
修复的业务反例，不允许覆盖原始来源。状态“已处理”仍需真实回归证明。
